# Sherubtse Freelancing — UI and workflow delivery

The existing Express/EJS MVC application has been redesigned in place. No frontend framework or payment gateway was added. The logo artwork, all 36 existing page routes, all three calendar API routes, email verification, dual roles, PostgreSQL and MongoDB ratings remain in use. Six page routes were added for notifications, invitation responses and starting work.

## Run the updated project

Your current workspace has already received the UI migration, after a PostgreSQL custom-format backup. Do not replace your `.env`.

```powershell
npm.cmd install
npm.cmd test
npm.cmd run check:ui
npm.cmd start
```

Open http://localhost:3000. Use `npm.cmd run dev` for development.

For another existing installation with profiles/calendar already installed:

```powershell
npm.cmd install
npm.cmd run migrate:ui
npm.cmd start
```

If the older profile upgrade has not yet been installed, first run `npm.cmd run migrate:verification` and `npm.cmd run migrate:profiles`, then `npm.cmd run migrate:ui`. Do not rerun older migrations over an installation that already uses the new invitation/progress statuses.

For a completely new installation, create `sherubtse_freelance_db` in pgAdmin. Run `database/postgresql_schema.sql`, then `database/profile_calendar_migration.sql`, then `database/ui_workflow_migration.sql` in that order. Copy `.env.example` to `.env` only for a new installation and supply your own database, session and Gmail settings. Start MongoDB; set the administrator variables and run `npm.cmd run seed:admin` if needed.

The ZIP contains complete source, placeholder environment examples, documentation and preview screenshots. Dependencies, private database dumps, browser caches and the real `.env` are excluded. Run npm install after extracting it.

## Database changes and backups

The new migration is transactional and can be rerun. It adds programme/year, contact, experience and preferred hours to student profiles; requirements to work; a decision note to applications; invited, declined and in_progress statuses; and owner-scoped notifications generated by application-status changes. Status history supports the new states. `availability_before_work` remembers a student's previous manual setting so completion can restore it without overriding a subsequent deliberate change.

No tables are dropped and existing records are retained. MongoDB needs no changes. You may apply `database/ui_workflow_migration.sql` manually in pgAdmin after a database backup instead of using the command. The command first creates a pg_dump backup and stops if backup fails. `PG_DUMP_PATH` can specify your pg_dump executable.

Source backups are in `backups/before-ui-redesign/`. Database backups are named `backups/before-ui-workflow-*.dump`. Keep database backups private. Restore a dump through pgAdmin Restore if necessary; restore matching source files as well. Never distribute the backups folder.

Database-backed tests were possible with the existing configured services. No database credential blocker remains. Physical-device interaction, a screen-reader review, full keyboard walkthrough, real Gmail delivery and deployment-specific behaviour still require manual review.

## Manual review checklist

1. Register student, employer and dual-role accounts; verify the student email format, account-type explanation, password toggle, actual verification email, expired link and resend flow.
2. Log in as each role; navigate by keyboard and mobile menu. Check that employers awaiting approval cannot publish, while a dual-role account retains student access.
3. Edit programme/year, biography, selected/custom skills, contact, experience, preferred hours and availability. Reload to confirm persistence. Check business type/Other, name, location and contact fields.
4. Approve/reject employers as administrator, including a rejection reason. Filter/search accounts by verification, role and approval, and applications by progress. Confirm unauthorized accounts cannot open administrator routes.
5. Publish, schedule, save/edit/publish a draft, close and cancel work. Check requirements, wage unit, worker count, application dates and work dates. Verify invalid date ordering and own-post application denial.
6. Apply to two overlapping postings. Accept one; confirm availability becomes inactive and the other application is automatically withdrawn with an explanation.
7. Send an urgent invitation. Verify that it does not accept the student or withdraw other applications before consent. Confirm/decline as the student. Try confirming another student's invitation and filling the last position concurrently.
8. Start accepted work, complete it, submit a rating and check student feedback. Confirm that completing the last active placement restores the saved availability setting, while a deliberate manual change is retained.
9. Check read/unread notifications, links, timestamps and mark-one/all controls with two separate accounts; another account's notifications must not change.
10. Check calendar opening/closing dates, deadline markers, today, previous/next/month navigation, agenda, tasks, refresh errors and role privacy. Confirm `/api/calendar` still loads for authenticated users.
11. Review 360px phone, tablet and desktop layouts with long real names/descriptions and large datasets. Check search reset, pagination, stacked application records and horizontal admin-table scrolling.
12. Review keyboard focus and screen-reader labels, and verify that all agreed wages are informational with no online payment flow.
